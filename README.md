# PrepBuddy

A practice web app for competitive exam aspirants. Each module contains small games designed to build calculation speed and accuracy.

## Speed Math module

- **Tables Practice** — multiplication drills across any combination of tables from 1 to 30 (e.g. `28 × 17`). Pick which tables to drill, get instant right/wrong feedback, and skip a question you don't know.
- **Squares & Cubes** — squares and cubes of 1 to 30, in squares-only, cubes-only, or mixed mode.
- **Ratios to Percentage** — convert fractions to percentages to two decimal places (e.g. `1/9 = 11.11`), with a basic (1/n) and advanced (n/d) difficulty.

- **Factor Pairs** (Maths hub, `/maths/factor-pairs`) — you get a number such as `72 = _ × _` and type every pair that multiplies to it (`8 × 9`, `4 × 18`, `6 × 12` …). Order does not matter: `8 × 9` and `9 × 8` are the same pair and count once. A pair can be typed as `8x9`, `8 9` or `8*9`. A wrong product is a mistake; a repeat or a pair the filters do not count (see below) is only a note. When all pairs are found, or you tap *show all pairs*, the full list is shown with the found ones ticked. Filters on the setup screen: **number range** (e.g. 50–120) *or* **tables × multipliers** (e.g. tables 11–19 × 11–20, which gives every distinct product 121…380); include `1 × N` or not; only count pairs whose factors lie in a range; the minimum number of pairs a number must have (Any, 2+ … 6+, which also drops primes); show the pair count as a hint or hide it; 5–20 numbers per session. The last settings are remembered in the browser. Logic is in `src/lib/factorPairs.ts`; `npx tsx scripts/verify-factor-pairs.ts` checks it against brute force.

- **Quadratic Equations section** (Maths hub) — the Game (`/maths/quadratic-equations`, generated practice) and the **Quadratic Question Bank** (`/maths/quadratic-bank`). In the bank you paste the two equations of a question (`I. 6x² − 5√6x + 4 = 0` / `II. 4y² − 11√7y + 42 = 0`, any reasonable paste: `x^2`, rearranged sides, `1.)` numbering, both on one line); the instruction line, the five options and the answer are made for you. The answer and a step-by-step solution (quadratic formula, simplify the square root, both roots, an approximate-value table, and the comparison) are worked out **exactly** with surds by `api/_lib/qbQuadratic.js` — no AI, so no wrong keys — which the browser uses for the live preview and the server re-runs to save, so a browser cannot store a made-up solution. Equations up to degree 2 are read, with rational or one-√ coefficients; cubics, a variable in a denominator and the like are refused with a reason. Saving needs a signed-in, email-verified account (`POST /api/qb?action=addquad`). Questions go into the same shared bank as the Quant Question Bank (topic Quadratic Equations), so they can be played, starred and exported there. **Duplicates** are caught on the canonical form of the equations (`6x² + 4 = 5√6x`, `12x² − 10√6x + 8 = 0` and `6x^2-5√6x+4=0` are one question), against both added and launch questions; swapping I and II is a different question. After regenerating the launch bank run `npm run build:quadkeys` (`build:qbank` does it too). `npm run verify:quadratic-bank` checks the solver against a floating-point oracle on thousands of random pairs and against the stored answers of the 199 launch questions it can read.

Every game auto-advances on a correct answer, clears the box for another try on a wrong one, and tracks accuracy, time, and mistakes per session. Session history is stored locally in the browser (no account or server needed); signing in syncs it across devices (see below).

## Tech

Vite + React + TypeScript + Tailwind CSS. Routing uses `HashRouter` so it works on any static host without server-side rewrite rules. Most game data is bundled statically with no backend; Vocabulary and Idioms are the exceptions — see below.

### Shared banks (Firebase Firestore)

All six English games are backed by [Firebase Firestore](https://firebase.google.com) instead of static data, via the generic helper in `src/lib/sharedBank.ts`:

- **Vocabulary, Idioms, One Word Substitution, Phrasal Verbs** — anyone can add an entry (looked up via Wiktionary's free API); it's saved to Firestore and visible to every visitor. Deleting an entry (built-in or user-added) is permanent and global. One Word Substitution's add flow takes just the single word and swaps the looked-up fields, since that bank stores the phrase as `term` and the word as `meaning` (reversed from the others, to match the real exam format) — its security rule's size limits are swapped to match (`term` gets the generous 2000-char cap since it holds the full descriptive phrase, `meaning` gets the tight 100-char cap since it's just the one word).
- **Vocabulary, Idioms, One Word Substitution, and Phrasal Verbs** all carry an optional `createdAt` ISO timestamp on every `BankEntry` (all seed entries are backdated to `2026-01-01`, new entries get the real add time). Their quiz setup screens show a **Freshness** filter (Any time / Days / Weeks / Months, with preset amounts like "Last 7 days") that restricts the question pool to entries added within that window — `BankQuiz` shows this section automatically whenever the bank it's given has `createdAt` on at least one entry, so any other bank can opt in later just by setting the field. Entries without `createdAt` are treated as "not recent" once a specific window is selected.
- **Synonyms, Antonyms** — these two games share a single **word bank** (`src/data/wordBank.ts`, `src/lib/wordBankStore.ts`) rather than each having its own: one entry per word carries its own meaning/example/part of speech *and* a full list of synonyms *and* a full list of antonyms (`WordEntry` in `src/lib/types.ts`), so the Synonyms and Antonyms games are just two different quizzes over the same underlying data. Anyone can add a word — the add flow looks up the word's own meaning, part of speech, and example automatically, and the user types the synonym/antonym lists by hand (comma-separated) since Wiktionary/Gemini can't be relied on to enumerate them. Those typed lists aren't trusted verbatim: `lookupWordBankEntry()` (`src/lib/dictionaryApi.ts`) asks Gemini to verify them in the same call — dropping words that don't actually belong (including one listed under the wrong side, or under both, like "increase" as both a synonym and antonym of "abate"), fixing obvious misspellings, and topping up a thin list with well-known correct words — and the add screen shows exactly what changed, if anything. Without Gemini available, it falls back to just removing any word listed as both a synonym and an antonym (the one check that needs no AI). A new word is starred as a favourite automatically. Deleting an entry is permanent and global. `WordEntry.createdAt` is always set (not optional), so their quiz setup screens (`WordBankQuiz`) always show the same **Freshness** filter described above.

This needs a free Firebase project of your own:

1. Create a project at the [Firebase Console](https://console.firebase.google.com) (free Spark plan, no card required).
2. Build → Firestore Database → Create database → start in **production mode**.
3. In the Rules tab, paste the contents of [`firestore.rules`](firestore.rules) and publish (or run `firebase deploy --only firestore:rules`). That file is the single source of truth for the rules; they enforce, per collection:

   - **Custom entries** (`*CustomWords`): created only with an id of the form `custom-<slug>` that matches the document's own `id` field, with exactly the expected fields (no extras) and size limits; deleting is allowed only for `custom-…` ids; an existing entry can only have its `difficulty` changed. One Word Substitution has the term/meaning size limits swapped because it stores the phrase as `term` and the single word as `meaning`. Phrasal Verbs has no difficulty editing, so its `update` stays blocked.
   - **Hidden built-in entries** (`*HiddenSeedWords`): a document may contain only `{ hiddenAt: <number> }`.
   - **Difficulty overrides** (`*DifficultyOverrides`): only `{ difficulty, updatedAt }`, written with `setDoc`. The Library saves a built-in entry's new difficulty here (it can't edit bundled data), and layers it over the bundled entries on every read; without these rules the Library's difficulty control fails with "Missing or insufficient permissions".

   The `synonymsCustomWords`, `synonymsHiddenSeedWords`, `antonymsCustomWords`, and `antonymsHiddenSeedWords` collections/rules from the old separate Synonyms/Antonyms banks are no longer read or written by the app (superseded by `wordBank*` above) — safe to delete from your rules whenever convenient, or just leave them as harmless dead rules.

4. Project settings → Your apps → add a Web app → copy the `firebaseConfig` object into `src/lib/firebase.ts` (this config is safe to commit; it's not a secret — access is controlled by the rules above, not by hiding these values).

There are no accounts in this app, so with no login system these rules intentionally allow anyone to add or delete any entry. That's a deliberate trade-off for a fully static, backend-free deploy — don't reuse this Firebase project for anything that needs real access control. The rules do stop malformed or oversized writes, arbitrary document ids and extra fields, but they cannot stop someone from *scripting* valid adds/deletes. Two things limit the damage:

- **Reads go through a CDN-cached route.** The Library, Quiz and Hub screens load each bank through `/api/bank` (`api/bank.js`), which reads a collection from Firestore once and lets the Vercel CDN serve it to every visitor for an hour (stale copy for up to a day while it refreshes). Firestore reads therefore stay roughly flat as traffic grows instead of scaling with visitors; a visitor who has just edited a bank skips the CDN copy for 10 minutes so they see their own change. If the route is unreachable the app falls back to reading Firestore directly, and if Firestore itself is unavailable (down, quota used up, offline) every screen still works from the bundled built-in entries and shows a notice.
- **Optional hardening (recommended once you have real traffic).** Create a service account for the project (Firebase Console → Project settings → Service accounts → Generate new private key), and add its JSON to Vercel as the environment variable `FIREBASE_SERVICE_ACCOUNT` (raw JSON or base64) and redeploy. `/api/bank` then reads Firestore with that identity, so you can lock bulk reads in `firestore.rules` by replacing every `allow read: if true;` with `allow get: if true; allow list: if false;` — nobody else can list or scrape the collections, while visitors keep getting data through the cached route. (Single-entry lookups with `get` still work.) Turning on [Firebase App Check](https://firebase.google.com/docs/app-check) for Firestore is the next step if someone starts scripting writes.

### Mnemonic Vocabulary (static bank, no backend)

`/english/mnemonic-vocab` is a separate, fully static bank of 1,018 words from a mnemonic-vocabulary book: each word has a cartoon, respelling (with a speaker button), part of speech, Hindi + English meaning, a memory trick, synonyms, antonyms and two example sentences. The words live in `src/data/mnemonicVocab.json` (its own lazily-loaded chunk) and the pictures in `public/mnemonic/img/`; see `scripts/mnemonic-vocab/README.md` for how they were extracted.

- **Learn today** — each day you get 5/10/15/20 *random* words picked from the words you have not learned yet, from the whole A–Z range rather than the next ones in order. A word only counts as learned when you tap **I have learned this word** (just viewing it does nothing); words you skip stay in the pool and can come back another day. The set stays the same all day (and resumes at your first unlearned word), "Get N more" draws a fresh one, and an A–Z strip shows how much of each letter you have learned. Star a word to add it to favourites. Shared with the Hindu bank: `src/lib/dailyLearn.ts` + `src/components/LearnToday.tsx`.
- **Word library** — browse/search all words; filter by ★ favourites (with the usual "last N days" recency chips), not learned yet, learned; each card has a mark-as-learned button.
- **Revise favourites** — the game. Pick a *freshness window* (favourited within the last 1/2/3/7/14/30 days, or any time), a mode (Picture → Word, Word → Meaning, Mixed) and what to ask first when there are more favourites than questions (freshest, weakest — missed last time / never asked / asked longest ago — or random). Wrong options are the same part of speech and never a synonym of the right answer. After each answer the full card is shown so the mnemonic sinks in; un-starring a mastered word drops it from revision.

Favourites (key `mnemonic-vocab`, same store and timestamps as the other banks), learned words and per-word revision stats are kept in this browser's localStorage. `npm run verify:mnemonic` checks the data and the game logic.

### The Hindu Vocabulary (static bank, no backend)

`/english/hindu-vocab` is a second static bank: 1,787 "power words" from The Hindu editorials, each with a Hindi and an English meaning, five synonyms, five antonyms and two example sentences (the book has one; the second was written for every word). Data lives in `src/data/hinduVocab.json` (its own lazily-loaded chunk); see `scripts/hindu-vocab/README.md` for how it was extracted.

- **Learn today** — the same random-unlearned-words-each-day flow as Mnemonic Vocabulary (mark each word learned yourself; A–Z coverage strip; "Get N more"), using the shared `LearnToday` component.
- **Study the words** — search (word, meaning, Hindi, synonyms, antonyms), jump to a starting letter, filter by ★ favourites / not learned yet / learned, mark words learned, star favourites (same store and "last N days" chips as the other banks, key `hindu-vocab`).
- **Practice game** — reuses the standard MCQ runner (hints, skip, timer, review with explanations, "Best %" on the English hub). Pick a type — *Meaning*, *Hindi → Word*, *Synonym*, *Antonym*, *Fill the blank* (an example sentence with the word blanked out) or *Mixed* — plus a starting letter, favourites-only (with recency) and 10–50 questions. Wrong options are the same part of speech and never a synonym of the right answer; synonym questions always include one of the word's antonyms as a trap (and vice versa); fill-the-blank only uses sentences where the word appears once in its base form (1,754 of the 1,787 words).

`npm run verify:hindu` checks the data and every question type; `npm run verify:learn` checks the shared Learn today logic.

### Saved progress follows you across devices (sign-in)

Favourites, learned words and game progress live in the browser's localStorage, so everything works signed out and offline. When someone **signs in** (Google or email), `src/lib/sync/` mirrors that data to the server so it follows them from device to device — in every section and game, with no changes needed in the screens that save it.

- **What is synced** (`src/lib/sync/collections.ts` is the single list): favourites in every word bank (Vocabulary, Idioms, One Word Substitution, Phrasal Verbs, Word Bank, Mnemonic, The Hindu), learned words (Mnemonic, The Hindu), every game's session history and sprint best scores, Grammar Rules mastery and Mnemonic revise stats. The question bank's stars and answers keep their own older sync (`src/lib/qbank/sync.ts`). **Not synced on purpose:** caches (pronunciations, generated papers), unfinished-quiz drafts, per-device settings (theme) and full Mock / Daily-exam attempts (large). To sync a new kind of data, add its key pattern to `collections.ts`.
- **Existing users:** the first time an account signs in on a browser, *everything already stored there* (from before accounts, or before this feature) is captured and merged into the account automatically. Signing in on a second device merges that device's local data with the account's the same way, so nothing is lost on either side.
- **Merging:** per entry, the most recently changed version wins, and a removal (un-starring, un-learning) is recorded as a deletion marker so it reaches the other devices; an old offline device can never undo a newer change. Best scores keep the highest ever. If a *different* account signs in on the same browser, the first account's local copy is cleared (it is safe on the server) instead of being mixed into the second.
- **How:** after anything writes to a synced key, a few seconds later the key is compared with a shadow copy and the changes are queued (in localStorage, so a refresh or being offline loses nothing) and sent in one request; opening the site (and coming back to the tab after 5+ minutes) does one "full" sync that also brings back everything from the server. If the screen on display was built before the first sync brought in other devices' data, it is refreshed once.
- **Server:** `POST /api/qb?action=usersync` (`api/_lib/userSync.js`, behind the same Firebase sign-in check and rate limit as the question bank) — one Upstash Redis hash per user (`usd:<uid>`, one field per entry). It uses the same `UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN` as the question-bank sync, so no new setup; without them the browser simply keeps working locally and retries quietly. A push costs 2 Redis commands, opening the site 1–2, against the free plan's 500,000 a month. Limits: 40,000 entries per user, 600 per request. Deletion markers older than 120 days are forgotten.
- `npm run verify:usersync` checks the key mapping, the server's validation and merge, and the browser engine with several simulated devices (account created after local data existed, offline changes, a second account on one browser, a big first upload).

### Security headers and abuse limits

- `vercel.json` sends `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy` (microphone for voice input only), HSTS and a **Content-Security-Policy** (`script-src 'self'`, no inline scripts — the theme bootstrap lives in `public/theme-init.js`; `connect-src` lists only this site, Firestore, Wiktionary and dictionaryapi.dev). If you add a new third-party API or script, add its origin there or the browser will block it. Hashed files under `/assets` are cached as immutable.
- The serverless functions share a rate limiter (`api/_lib/guard.js`): lookup 30/min, game generators 20/min, mock English 40/min, puzzle screenshots 12/min per visitor. It counts in memory per server instance by default; for one exact limit across all instances, add a free [Upstash Redis](https://upstash.com) database and set `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN` in Vercel. Model calls are hedged (the second model is only asked if the first is slow or fails), the Gemini key travels in a header rather than the URL, and upstream error text is logged on the server, never sent to the browser.
- Known remaining limits: `npm audit` still lists 4 findings inside Firebase's Node-only gRPC packages (not part of the browser bundle; clearing them needs a breaking `firebase` downgrade), and the model-health cooldowns in `api/mockEnglish.js` are per server instance.

### AI-assisted lookups (Gemini)

Every "Add" flow looks up its word/idiom/phrase via `lookupWord()` in `src/lib/dictionaryApi.ts`, which tries a Gemini-backed serverless function (`api/lookup.js`) **first**, since Gemini reliably returns both a meaning and a natural example together. Wiktionary's free REST API is the fallback — used only if Gemini is unavailable (no key configured, network error) or genuinely finds nothing — since on its own it has real gaps: it only matches exact page titles (missing many real idioms and loosely-worded phrases) and, even when it finds a definition, often has no example sentence for that particular sense. This benefits every bank that shares `lookupWord()`: Vocabulary, Idioms, One Word Substitution, Phrasal Verbs, and the word half of Synonyms/Antonyms.

The Gemini API key must **never** be shipped to the browser (unlike the Firebase config above, it's a real secret), so the call happens server-side in a Vercel serverless function rather than directly from the React app:

1. Get a free API key at [Google AI Studio](https://aistudio.google.com/apikey).
2. In the Vercel project, go to Settings → Environment Variables and add `GEMINI_API_KEY` (all environments), then redeploy.
3. By default `api/lookup.js` tries `gemini-3.5-flash` first, then falls back to `gemini-3.5-flash-lite` if that call errors, times out, comes back malformed, or says "not found" — the fuller model handles trickier inputs better (e.g. an idiom with a pronoun swapped or verb conjugated, like "cash in one's chips" typed as "cashed in his chips"), and the second model is a real second opinion rather than just a health check. Optional: set `GEMINI_MODEL` to pin a single specific model instead (skips the fallback entirely) — useful if Google renames or deprecates one of the two; check [ai.google.dev/gemini-api/docs/models](https://ai.google.dev/gemini-api/docs/models) if lookups start failing.

Without this env var configured, `api/lookup.js` returns a clear 500 error and every "Add" flow transparently falls back to Wiktionary (and from there to the original "No definition found" message if that fails too) — nothing breaks, Gemini is just skipped. Note that `api/lookup.js` only runs as a real serverless function once deployed on Vercel; `npm run dev` (Vite) serves it as a static file instead, so only the Wiktionary path can be exercised locally without the Vercel CLI (`vercel dev`).

### Grammar Rules → Fresh Sentences (AI-written practice)

`/english/grammar-rules/fresh` quizzes only the rules the learner has **started** (the "N of 120 rules started" count on the Grammar hub: opened in Rule Lab or answered in any game). For every question an AI writes a brand-new sentence for one of those rules, never one from the book, and the learner names the rule it breaks or shows. Spaced-repetition progress is updated as in Spot the Rule; the AI's one-line explanation is shown after each answer, and a sentence that looks faulty can be reported (it is then not scored).

- **Server:** `api/freshSentences.js` (POST, `GEMINI_API_KEY`, same model chain and rate limiter as the other generators; shared Gemini helpers in `api/_lib/gemini.js`). It receives the rule's title/summary/explanation/book examples plus the random ingredients below, and only returns sentences that are well-formed, differ from the book examples and recent sentences, and (for errors) differ from their fix.
- **Randomness:** the client attaches fresh random ingredients to *every* question: a setting (~70), a register (12), a length, two random prompt words (~150) and sometimes a name (~40), see `src/lib/freshSentenceSeeds.ts`. The server adds a random model seed, and the browser remembers the last 12 AI sentences per rule (`prepbuddy:grammar-fresh:sentences`), sends the latest as "do not repeat" and rejects repeats.
- **Client checks:** `src/lib/freshSentencesApi.ts` also rejects anything matching a rulebook sentence, anything already used this session or recently, and an "error" sentence whose fix is a wholesale rewrite. Failed slots get one top-up pass.
- There is deliberately **no fallback to book sentences**: if the AI is unavailable the game says so and lets the learner retry. Like the other AI features it only works where the serverless function runs (Vercel, or `vercel dev`).

## Reasoning → Puzzle Solver (any floor / seating puzzle, step by step)

`/reasoning/puzzle-solver` takes the **text** of a "people on floors / in a row, each with a city, colour, …" puzzle (paste it, or drop / paste / choose a **screenshot**) and solves it while teaching it:

- **Why this clue first.** Facts that are stated outright ("W is from Pune", including the free half of "A, who is from Kolkata, lives on …") go on the board first. After that every unused clue is tried on the board as it stands and scored by how many possibilities it removes; the best one is used and the whole ranking is shown as bars, with a plain-English reason (it pins one person, only ties two people, or is about someone not yet identified) and what was already known about the people it mentions.
- **Why not anywhere else.** Every possibility that is crossed out keeps its reason ("A on floor 8 would put X on floor 9 — there is no such floor"). Each step lists the people / values it placed or narrowed, with a pip per floor and the grouped reasons.
- **What if it were placed differently.** Click any crossed-out option: the puzzle is replayed from that step with the option assumed true, and the board animates the consequences (amber = supposed, red = clash) until a contradiction ends it. When nothing a single clue can settle remains, the step is a *case analysis* ("if N were on 8 …"), each test replayable the same way.
- The board is animated from the engine's event log (chips struck out, locked in, flashing on a clash); `prefers-reduced-motion` shows each step's end state at once.

How it works (`src/lib/puzzleSolver/`):

| file | role |
|---|---|
| `parse.ts` | text → people, floors or row, extra categories, and clue *atoms* (immediately above/below, N floors above, between, N people between, adjacent, topmost / lowest / odd / 3rd from the top, "is from", negations, "A, who is from X, …", two statements joined by "and"). Anything it cannot read is listed and never guessed at; the UI shows how every clue was read before solving. |
| `engine.ts` | logic-grid model (people × positions × each category), propagation with a reason for every crossing, exhaustive search (`enumerate`) and an independent `failedClues` check |
| `trace.ts` | the planner (clue choice, beats, "why not" rows, case analysis, `simulate` for what-ifs) |
| `ocrApi.ts` + `api/puzzleOcr.js` | screenshot → text: the image is downscaled in the browser, `api/puzzleOcr.js` (POST, `GEMINI_API_KEY`, same rate limiter and model chain, 12/min) only *transcribes* it into the text box so it can be corrected; magic bytes and size are checked server-side |

**Round table of unknown size** ("A certain number of persons are seating a circular table facing the centre … At least fifteen persons are sitting around a circular table"): only some people are named, so every size from the stated minimum up to 24 is tried, the sizes the clues allow are reported ("only 15 persons fit every clue") and the people the text does not name are shown as ?1, ?2 … (`Puzzle.anon`: they are interchangeable, so the engine takes them in seat order). "Not more than six persons between U and V, counted from the right of U" is a diff atom with several allowed distances (`ds`), and "Y is neither neighbour of W nor X" / "Z is neighbour of neither X nor W" read as two "not next to" clues. The solver now accepts up to 24 people (the candidate masks are 32-bit).

**Only some people have a value** ("Events, whose name starts with consonant, are held in different states among …", six states for nine events): the missing ones are padded with identical "(none)" values (`Category.padFrom`; the engine hands them out in list order so the padding adds no extra arrangements), and a clue lists that the vowel events are not in any state. Also read now: two subjects or two objects in one relation ("O and E are held after R", "S is before N and M"), a "which" clause as a statement of its own ("…, which is held in August"), and "…, but in different months" after a relation.

**Two rows described in one sentence** ("Seven persons H … are sitting in Row 1 facing north whereas P … are sitting in Row 2 facing south such that both rows are equidistant and parallel") are split into one sentence per row; "sits 4 th to the right" (a gap copied into the ordinal), "Either M or K sits at one of the extreme ends" (the shared predicate applies to each person; "either" = exactly one) and "T does not face K or M" (denied of both) are read too.

**A row of unknown length** ("Certain number of persons are sitting in the straight row … not more than two known persons sit on the adjacent seats") works the same way, with the number of named people as the minimum size: every size up to 24 is tried and, here, the "at most two named people side by side" rule (`Puzzle.maxNamedRun`, applied by the engine in every step and shown as a clue with no reading of its own) is what separates 19 persons from 17. The unnamed-people and no-value orderings are free choices, not clue deductions, so their crossed-out options say so (`why.kind: 'sym'`, like the round-table rotation).

An **Instructions** button to the right of the page title (`src/components/puzzle/Instructions.tsx`; Escape or a click outside closes it) lists how the solver reads a puzzle — keep it in step with the parser. Among the rules: when months, years or weekdays are listed with gaps (Jan, March, May, August), "three months before" is the **real calendar gap** (May → August; the parser marks such clues `by: 'value'` and `Puzzle.values` carries the month numbers), while "three persons before" is three places in the list; "L promoted three persons before M" has two people between them; "either … or" means exactly one and "neither … nor" rules out both; and in floor puzzles "n persons between" counts people while "n floors between" counts floors (the empty one too).

The solution is accepted only when an exhaustive search finds exactly one arrangement and every clue holds when evaluated directly; if the clues allow several arrangements or none, the walkthrough says so (and, for none, names the clues whose removal makes it solvable). Supported: 3–12 people on **floors** (numbered from the bottom or the top), in a **row**, on named ordered slots (**months or weekdays**, e.g. "from May to December") around a **round table where everyone faces the same way** (left/right as each person faces), or in a **building with several flats on each floor** ("a four storeyed building, each floor has 2 flats, Flat A and Flat B"; clues like "same floor", "different lettered flats", "south-east of", "above … in the same type of flat", "even-numbered floors", "in flat A but not on floor 1"; person letters and flat letters may coincide), or as **boxes kept one above the other in a single stack** ("The box, which contains Mango, is placed three boxes below the box L", "Box H is a prime numbered box"; plural/singular spellings of a value, such as "Bananas" and "Banana", are the same value), or **fewer people than the floors of a building** ("eight people live in a nine-storied building": the people are taken in floor order; "floors above / below / between" and "immediately above" count floors, the empty one too, while "persons between" counts people; "on the perfect cube / perfect square / prime numbered floor", "above S but not immediately above"), or **people born in different years with clues about their ages** ("born in 8 different years i.e. 1998, 2005 …", "The base year for the calculation of their ages is 2023"; "the age of F is a perfect square / a multiple of 11 / odd / more than 30", "the difference between the ages of G and A is the same as between F and C", "the number of persons born after F is the same as the number born before B"), or **people in numbered classes with seniority** ("eight different classes i.e. class 1, class 2 … class 8", "immediate senior / junior to H", "senior to", "even numbered class", "Three persons are between the classes in which F and H studies"; a higher class is more senior), or **fewer people than the days of a week** ("six friends buy six bikes in a week starting from Monday … one day no one purchases": the people are taken in order of their days, "days after / days between" count days — the vacant one too — while "persons between" counts people, and "No bike is purchased on the day in the middle of the week" fixes the vacant day; pasted markdown links such as [Hardik](https://…) are read as the plain name), or **candidates with two-letter names that are only used in the clues** (Aa, Ab, Cc …, taken from the clues when their number matches "Eight candidates"; the months in one sentence and the dates in the next), or **seven people on the days of a week** ("buy seven different bikes … in a week", "The week is starting from Monday"; "buys either KTM or Yamaha", "buys Benelli on the penultimate day", "in the middle of the week", "after two days of the one who bought Ducati", "three days between …", "No one buys after Rohit"), or in a **row where everyone faces south** ("All of them face towards the south": a person's left is then the east, so "to the left of" means further east; the answer is drawn west → east like the picture; "Neither G nor the one who likes Black sits at the extreme end", "the number of persons to the right of B is equal to the number to the left of …"), or on **dates of a few months with any number of dates per month and, when there are more dates than people, some of them vacant** ("the 16th and 25th of three different months", "on an even-numbered date", "neither in October nor on the 16th", "more than one person between L and I"; with vacancies the people are taken in date order and "after" / "between" count people, not empty dates), or with **no seating at all** (people matched with cities and bikes: "Seven persons … live in different cities among …", "Neither F nor B likes Bajaj and Hero"; the first attribute stands in for the positions, and when several arrangements fit the page shows what they agree on — bold — and the alternatives left open), or in a **line with ranks given only as a range** ("different ranks from I to VI", then "IIIrd rank", "Vth rank", "the top rank"; "second from one of the ends"; "as many persons to the left of … as to the right of …"), or around a **table with corners and sides** (square, pentagon-shaped, hexagonal: one person on every corner and on the middle of every side, the corners facing outside or the centre as the text says and the sides the other way; left / right are as seen by the person the clue is about, so a corner and a side have opposite "right"; "I sits immediate right and immediate left of A and C respectively", "sit opposite to each other", "doesn't sit immediate right of M and S", "faces towards the centre / away from the centre"; fruits and the like may be introduced by "among"; "second to the left of", "counted from the right of W", "at one of the corners", "faces" = across the table on a side; turning the table by two seats changes nothing, so the first step puts one person in seat 1 or 2), or in a **line where some people face north and some south** ("Some of them are facing south while some are facing north": left / right are taken as seen by the person named after "of", which is the reading that gives one answer on the exam puzzles; "B and I face the same direction", "L faces south"; the people and the values of an attribute may be left unlisted, in which case they are taken from the clues and the page says so), or on **dates of a few months** ("birthdays in January, April, May and September on two different dates, 11th and 16th": "in the same month", "on the same date but in different months", "in the month having 31 days", "before B on the 16th", "not more than four persons before E", "B, who was born in April"), or in **two parallel rows facing each other** ("In Row1- A, B, C … facing south. In row2- L, M, N … facing north.", or one list of names with "sits in row 1" clues; left/right are each person's own, seat 1 of a row is that person's left end, and the person directly opposite is the one facing them; clues such as "third to the right of the one who faces E", "O neither stands opposite C nor F", "the number of persons to the left of D is the same as to the right of A", "in the same row as", "at the end of the row"); any number of extra categories; as many people as floors/seats. Clues: above/below/before/after (also "third to the left of", "N floors above"), neighbours, "N people between" (also "…when counted from the left/right of X"), "the same number between X and Y as between Z and W", exactly opposite / "faces", first / last / odd / even / prime / multiple of 3 / weekend / 31-day month, "N people above A", negations, "Neither A, B nor C …", and the compound forms **"If … then …"**, **"Either … or …, but not both"** and "Either … or …". On a round table the solver first fixes one person in seat 1 (turning a round table changes nothing) and says so; seat numbers are then labels. Not supported yet: tables where some people face the centre and others face outside, rectangular tables, rows of unequal length, boxes in several stacks side by side, more floors than people, and "as many … as" comparisons other than the equal-gap clue above.

If the clues contradict each other, the walkthrough names the clues whose removal makes the puzzle solvable and, separately, any clue that — **read as its own opposite** — leaves exactly one arrangement (a "not" lost when a puzzle is copied is a common cause), with a one-click "solve with that reading".

Verification: `npm run verify:puzzle` also runs the app's **own mock-test generator** (`src/lib/mocks/reasoning/mains`) end to end — its printed puzzle text goes through the parser and solver, and the answer must equal the generator's hidden answer (round tables with one facing, single rows, two facing rows, floors, schedules). That test found, and the generator now fixes, a bug where a negated "N persons sit between X and Y" clue (and a negated "same number between …" clue) was printed *without* its "not", so the puzzle as printed contradicted its own answer; the generator now writes "It is not true that …" and throws if a negated clue ever lacks a negative wording. `npm run verify:puzzle` checks the parser on ~200 phrasings, the engine against brute force on random puzzles (floors, rows, months, round tables, flats and two facing rows, with compound clues and "the one who …" people), the soundness of every crossing, and that every what-if really ends in a contradiction (except seats ruled out only by fixing the first person on a round table, which it labels as a rotation).

## Mocks module

SBI/IBPS **PO (hard)** and **Clerk (medium)** prelims mocks at `/mocks`, in an exam window modelled on the TCS/NTA software (question palette with the five status shapes, per-section clocks, Mark for Review, Clear Response, Save & Next, Question Paper / Instructions, text-size control, submit summary, autosave/resume after a refresh). Three kinds per exam:

- **Full-length** — 100 questions, 60 minutes: English 30, Quant 35, Reasoning 35, 20 minutes per section. As in the real exam, sections are locked: you can't return to one after submitting it or when its time ends. +1 / −0.25.
- **Sectional** — one section at its real question count and time (English 30/20 min, Quant 35/20 min, Reasoning 35/20 min).
- **Topic-wise** — one topic, with your own question count (5–40) and 30–60 seconds per question.

The pattern and the per-section topic mix are in `src/lib/mocks/blueprints.ts` (taken from the 2025 IBPS PO, IBPS Clerk and SBI PO prelims shift analyses: puzzles/seating dominate Reasoning; DI + arithmetic + approximation/series dominate Quant; RC, cloze, error detection, para jumbles and fillers make up English). Some 2025 SBI PO shifts were reported with a 40/30/30 English/Reasoning/Quant split, but the coaching sources contradict each other, so the widely documented 30/35/35 is used for both exams — change the blueprint if you disagree.

**Where the questions come from, and how they are checked**

- **Quant** (`src/lib/mocks/quant`, 22 topics) — generated in code, designed backwards from clean numbers. Every generator cross-checks its key with a second method and throws if they disagree.
- **Reasoning** (`src/lib/mocks/reasoning`, 15 topics) — puzzles, seating, comparison and ranking are generated from a hidden arrangement and accepted only if an exhaustive solver finds exactly one solution; syllogism and inequality are decided by exhaustive model/assignment enumeration.
- **English** (8 topics) — comes from a **curated bank shipped with the app** by default (`content/english/*.json` → built into `src/lib/mocks/english/seed.generated.json`, ~300 questions: reading comprehension, cloze, error detection, para jumble, fillers, word swap, phrase replacement, match the column; PO = hard, Clerk = medium). It loads instantly, needs no internet or API keys, never repeats a question inside a paper, and prefers questions you haven't seen yet (tracked in the browser; repeats only start once a topic's pool is used up). Every item was written to a strict brief, then solved **blind by an independent reviewer** who fixed or deleted anything with a second defensible answer (logs in `content/english/_review/`). Several types are correct by construction: a word-swap's faulty sentence is derived from the authored correct one, para-jumble and match-the-column keys come from the authored order.
  - **Adding questions:** write items in `content/english/<topic>-<hard|medium>.json` (schemas and conventions in `content/english/README.md`), then `npx tsx scripts/build-english-seed.ts --blind` validates them (fails loudly with file/item-precise errors, proves the by-construction keys, rejects duplicates and skewed answer positions) and rewrites the seed; the `--blind` views in `content/english/_blind/` (git-ignored, no keys) are for a second person to solve before you trust the new items.
  - **Optional "Fresh AI questions"** (a switch on the launch page): written by an LLM, then solved blind by a second pass (a different provider/model where one is available) that must agree and judge exactly one option acceptable. It needs keys — set any of `GEMINI_API_KEY`, `GROQ_API_KEY`, `MISTRAL_API_KEY`, `OPENROUTER_API_KEY` (in `.env.local` for `npm run dev`, or as Vercel environment variables); chains can be overridden with `MOCK_ENGLISH_GENERATE_MODELS` / `MOCK_ENGLISH_SOLVE_MODELS` (`provider/model,…`). Models that are out of quota, removed or overloaded are skipped and remembered in the browser; verified AI questions are banked in the browser so "Try again" resumes; and anything the AI can't fill is taken from the curated bank, so this mode never leaves a mock unable to start. AI questions can't be proven correct, only filtered — the curated bank is the one to trust for serious practice.

  **Free-tier reality (AI mode only):** a full mock's English needs roughly 15–40 model calls. Gemini's free tier gives about 20 requests per day per model and Groq's about 8,000 tokens per minute per model, so on free keys only a few mocks a day are possible and a preparation may need a "Try again" after a minute. More providers (Mistral's free plan is the most generous) or billing on one key remove most of that friction. `npx tsx --env-file=.env.local scripts/probe-llm-models.ts` shows which models your keys can use right now and their limits; `scripts/verify-mocks-english.ts --live-paper` / `--live-review` time and dump a real section (they spend your quota).

`npm run verify:mocks` runs all four test harnesses (engine/timers/scoring/PDF, Quant, Reasoning, English with a stubbed Gemini; the Quant and Reasoning ones generate tens of thousands of questions). Once you have a key, `npx tsx scripts/verify-mocks-english.ts --live 10` measures how often the live model's questions are filtered out.

**Question Paper → Download PDF** — the exam window's Question Paper dialog can save the current section as a printable practice copy (questions and each set's passage/data, no answer key — so it can't be used to peek ahead in a locked full mock). Check your answers afterwards in the result's solution analysis.

**Result report** — overview, rank predictor, performance breakdown, sectional summary, compare-with-topper, topic analysis and the full question-by-question solution analysis, on screen and as a downloadable PDF (`src/lib/mocks/pdf.ts`, lazy-loaded). There are no other test-takers, so **rank, percentile, topper and average are estimates against a simulated cohort of 2,000** (`src/lib/mocks/cohort.ts`) and are labelled that way in the app and the PDF. Finished attempts are kept in the browser (last 12) and can be re-attempted. For every Data Interpretation set (table, bar, line, pie, caselet) the analysis re-expresses the given data as a **complete table with the derived columns/rows** (e.g. population and % literate → literate and illiterate people; pie → % / angle / number; Venn caselets → every region), and every quant solution is written **step by step** (`Step 1: … Step N: Answer = …`) with each derived value's working shown. The derived tables are analysis-only: they never appear during the test or in the downloadable practice question paper.

To run the Gemini-backed functions under `npm run dev`, put `GEMINI_API_KEY=...` in `.env.local`; `vite.config.ts` serves `/api/*` locally (it never reaches the browser bundle).

## Daily Dose of Practice

One fixed SBI PO-level quiz per section per day at `/daily`: **Quant (25)**, **Reasoning (25)** and **English (45)**, with no time limit. The paper is a pure function of the date (`src/lib/daily/compose.ts`), and it is cached the first time it is opened, so it is identical on every visit that day, on any device. Reopening a finished section shows the summary, and **Re-attempt** starts a new attempt on the same paper.

- **Quant / Reasoning** come from the mock generators (hard level) seeded from the date: Quant follows the reference practice sheet (simplification, approximation, arithmetic, quadratics, wrong/missing series, one DI set); Reasoning has a seating set and two puzzle sets at medium level (`src/lib/mocks/reasoning/mains/medium.ts`: the Mains engine with fewer attributes and clues), then Mains-level syllogism, inequality, blood relations, direction, ranking and input-output / data sufficiency.
- **English** follows the "English Daily Checklist": 10 error detection, 5 RC, 5 para jumble, 5 cloze, 5 sentence improvement, 5 vocabulary, 3 idioms, 3 phrasal verbs, 4 one-word substitutes. It uses the curated mock bank plus the built-in word banks and needs no network. Each topic walks its pool in a fixed shuffled order, so nothing repeats until the pool is used up (error detection after 4 days, RC and cloze after 8). Add questions to `content/english/` to lengthen the cycle.
- **Results** reuse the mock result page (score, rank/percentile estimates, breakdown, topic analysis, solution analysis). Daily attempts are kept in their own store (last 45) so they never push full-mock results out.
- **Download paper (PDF)** — the whole paper with the questions first, then an `Answers:` key and step-by-step `Solutions:`; every page carries the PrepBuddy header, watermark and footer (`src/lib/daily/pdf.ts`).

`npm run verify:daily` builds 40 days of every section and checks counts, determinism, day-to-day variety, validity and the PDF.
